# Sigma 코드 서식 규약 — 검사·적용 스킬

이 스킬은 두 가지를 제공한다.

1. **규약을 깊이 이해하기 위한 자료의 위치** — 정본 명세와, 규약대로 쓰인 워크드 예제(`app/`).
2. **기계검사 절차** — 빌드된 `sak` 프로그램으로 일부 규칙을 싸고 빠르게 1차 검출하는 방법.

경로는 모두 **이 프로젝트 루트 기준**이다(이 스킬은 `.claude/skills/sigma-style/`에 있으므로 루트는 세 단계 위).

## 1. 규약을 이해하는 법

### 1.1 정본 명세

- `Sigma_Coding_Convention.md` — **단일 정본.** 모든 판단의 근거는 이 문서다. 검사·수정 전에 통독한다.
  - §1 기본(행 폭·탭 들여쓰기), §2 제외 대상, §3 문법 강제, §4 토큰 분류(역할×이웃 방향), §5 괄호(단일행/다중행·가상 괄호·숨은 중괄호), §6 개행 우선순위, §7 개행 상태, §8 공백, §9 개행 원칙, §10 스타일(네이밍).

### 1.2 워크드 예제 — `app/`

`app/`의 소스는 **그 자체가 규약을 따라 쓰인 모범 예제**다. 규칙을 추상적으로만 읽지 말고, 이 코드에서 규칙이 실제로 어떻게 적용됐는지 대조하며 익힌다.

- `app/lexer.cpp`, `app/lexer.hpp` — **§2 제외 대상의 기준 구현.** 주석(`//`, `/* */` 다중행), 문자열(`"…"` 이스케이프), 문자(`'…'` 숫자 구분자 `1'000` 휴리스틱 포함), 원시 문자열(`R"d(…)d"` 다중행·접두사 `R/LR/uR/UR/u8R`), 전처리기 행(`#…` 통째·`\` 줄연장)을 좌→우 모드 추적으로 가려낸다. "무엇이 코드이고 무엇이 제외 영역인가"의 판단 기준으로 삼는다.
- `app/check.cpp` — **기계검사가 실제로 하는 일.** 어떤 규칙을, 원문 행 위에서 보는지 마스크 위에서 보는지, 위반을 어떤 좌표로 내는지 보여준다.
- `app/main.cpp` — CLI(대상 확장자·재귀·종료코드)와 출력 형식.

## 2. 기계검사(sak)가 커버하는 범위 — 가장 중요

`sak`은 규약 전체가 아니라 **렉서 수준에서 위양성 0으로 확실히 잡히는 규칙만** 검사한다. **v3.0.0(sak의 표기 판정 — "표기가 분류를 판정한다")에서 그 범위가 크게 넓어져, 이제 규약의 거의 전부를 sak 이 본다.** 1차로 sak을 돌려 걸러낸 뒤, 남는 것(4·5절)만 직접 검사한다.

> **`sak edit` 로 먼저 자동 교정.** `sak edit <file|dir>` 은 공백·탭만으로 결정적으로 고칠 수 있는 위반 — §8.4~§8.5 간격, §5.4~§5.6 구조적 들여쓰기 — 을 파일에 직접 적용하고(개행·비공백 불가침, 회귀 게이트로 증명), 나머지는 `[manual]` 로 남긴다. 먼저 `edit` 을 걸어 간격·들여쓰기를 넘긴 뒤 `[manual]` 잔여에 집중하면 토큰·시간이 준다. 자세히는 `sak_coverage.md` 2.5절.

### 2.1 표기가 분류를 판정한다 (v3.0.0, 가장 중요한 변화)

v2.2.0 까지 sak 은 문맥에 따라 분류가 갈리는 글리프(`* & && + - < > : << >> :: ! ~ ...`)를 **손도 대지 못했다.** 그 분류를 알려면 코드의 *의미*가 필요했고, 그러자면 파서가 필요했기 때문이다.

sak의 표기 판정은 화살표를 뒤집는다 — **작성자가 적은 표기(좌우 공백의 유무와 인접 토큰)가 그 분류를 판정한다.**

- `a * b` (양쪽 공백 + 양옆이 피연산자) → **양방향**(곱셈)
- `Foo *p` (왼쪽 공백 + 오른쪽에 선언 대상) → **단방향**(데코레이터)
- `int const * const *p` (이웃이 키워드) → 첫 `*` 는 **피연산**
- `Foo<T>` (`Foo` 에 붙은 `<`) → **여는 꺾쇠**. `a < b` (좌우 공백) → **비교**
- `case 1:` (붙은 `:`) → **단방향 라벨**. `class Foo : public A` (벌어진 `:`) → **양방향**

**어느 분류의 합법 표기와도 맞지 않는 표기(`a*b`·`a* b`·`int*p`)는 그 자체가 §8.4 위반**이다. 그리고 이 판정 위에 §8.4 문맥 의존 토큰, §9.1 개행 형태, §9.2 개행 경쟁 범위, §9.4 연산자 잔여, 그리고 꺾쇠 전량이 얹혀 내려왔다.

**패스 게이트:** sak 은 두 패스로 돈다. **1패스 위반이 난 행에서는 2패스(표기 판정에 기대는 검사)가 침묵한다** — 그 행의 배치를 믿을 수 없기 때문이다. 그러니 **보고를 고친 뒤 반드시 다시 돌린다.** 새 보고가 드러날 수 있다.

**용의(`[suspect]`):** 표기만으로 확정할 수 없는 충돌 사각(아래 4절)에서 sak 은 위반으로 단정하지 않고 용의로 지목한다. 종료 코드에 넣지 않고 `edit` 도 손대지 않는다.

**신호 공백 불가침:** 문맥 의존 글리프에 인접한 공백은 분류를 싣는 **신호**다. `edit` 은 그 유무를 뒤집지 않는다 — `a*b` 에 공백을 넣는 것은 서식 교정이 아니라 코드의 의미 선언을 바꾸는 일이다. 그런 자리는 `[manual]` 로 넘어온다.

### 2.3 sak 가 **검출하나 면제 판정이 필요한** 패턴

#### statement-like 매크로 호출 (`BEGIN_CODE_BLOCK(…)` / `END_CODE_BLOCK(…)` 류)

세미콜론 없이 끝나는 매크로 호출이 블록 가드 역할을 하는 패턴 (gtest `TEST(…){…}`, gmock `MOCK_METHOD(…)`, Boost `BOOST_AUTO_TEST_CASE(…)`, Qt 매크로 등). sak 가 §5.4·§9.3·§9.4 위반으로 잡지만 작성자의 의도적 관용구다.

**면제 휴리스틱** (다음 모두 만족 시 §5.4·§9.3·§9.4 검출을 면제):

1. 식별자가 **ALL_CAPS** (대문자·언더바·숫자만)
2. 식별자 직후 같은 행에 `(...)` 단일행
3. 그 행에 `;` 가 없음 (호출 단독으로 행이 끝)

만족 안 하는 자리 (`ASSERT_EQ(a, b);` 처럼 세미콜론 동반)는 정상 검출로 신뢰한다.

### 2.3.1 다중행 변수 선언 — 옛 "끝판왕"이 sak 전담이 된 자리

정본 형상은 하나다. **타입만 홀로 + 잉여 2칸 마커 / 선언자는 한 단계 깊게 / 마지막 행은 `;` 홀로.**

```C++
	Violation  
		v{
			t.row, t.col, "8.4", "…"
		}
	;
```

v3.0.0 부터 sak 이 **마커 없는 두 꼴을 모두 잡는다.**

- **① 단어 → 단어 개행** — `int const` 개행 `x`. 마커도 가상 괄호 키워드(`return`·`throw`·`using`·`case`)도 없다면 **어느 해석으로도 위반**이다: 변수 선언이면 마커 누락(§5.5), 아니면 인접한 두 비기호형 토큰의 개행(§9.3). 두 행 사이에 공행을 끼워도 같다 — 공행은 발생원이 아니다(§9.4).
- **② 이름이 타입에 붙은 채 `=` 로 이어짐** — `Violation v` 개행 `= {…}`. 타입과 이름을 한 행에 붙이면 마커가 설 자리조차 없다. **선언인지 아는 법**: 대입문의 좌변은 하나의 표현식이라 **피연산자가 둘 나란히 설 수 없다.** `result`·`obj.field`·`arr[i]`·`*p` 는 표현식(합법), `int x`·`std::vector<int> v`·`Foo *p`·`ns::Type v3` 는 선언(위반).

`Foo &a = func(` 처럼 `=` 까지 한 행에 붙인 꼴은 **§9.2 가 먼저 막는다** — 다중행 `(` 의 경쟁 범위(여는 행)에 단일행 `=`(괄호보다 높은 우선순위)가 앉기 때문이다. 그것을 고치면 `=` 가 내려오고, 그 순간 ②가 받는다. **고친 뒤 반드시 다시 돌려라** — 그래야 다음 보고가 드러난다.

### 2.4 sak 이 **못** 잡는 자리 — 이제 넷뿐이다

**v3.0.0 에서 매 파일 스윕은 사라졌다.** 옛 "top-notorious 표적 스윕"(§5.5 마커 없는 변수 선언)은 sak 전담이 되었고(2.3.1절), §8.4 문맥 의존 토큰·나체 꺾쇠·§9.1·§9.2·§9.4 잔여도 마찬가지다. 지금 사람이 볼 것은 **sak 이 자리를 지목해 주는 것들**뿐이다.

1. **`[suspect]` 용의 확정** — 표기 판정이 표기만으로 §8.4 분류를 확정 못 하는 충돌 사각. sak 이 자리를 찍어 주므로 **그 자리만** 본다. 네 꼴이다:
   - 문장 머리의 `식별자 * 식별자 ;` (`&`·`&&` 도) — 잘못 띄어 쓴 선언 / 옳게 쓴 연산 문장
   - 선언이 설 수 있는 괄호 안의 `식별자 & 식별자` — 잘못 띄어 쓴 매개변수 선언 / 옳게 쓴 이항 실인자
   - `식별자 < 식별자 > 식별자 ;` — 잘못 벌려 쓴 인스턴스화 / 옳게 쓴 비교 연쇄
   - 뒤에 떨어진 이름이 오는 피연산 데코레이터(`int * p;`)

   실측: 라이브러리 하나에 한두 건 수준. 선언이면 규약대로 붙여 쓰고(`Foo *p`), 연산이면 그대로 둔다.
2. **매크로 면제 가름** — 위 2.3절.
3. **§3 잔여** — 조건이 **3행 이상**인 제어문, **매크로가 본문을 제공하는** 자리의 중괄호.
4. **§2 한계 · §1.1 경계** — `#if 0` 비활성 분기의 보고는 무시. 전각 문자가 섞인 100자 경계 행은 직접 확인.

**알려진 거짓음성**(위양성 0 계약 때문에 일부러 침묵하는 자리 — 규약대로 쓰는 습관으로 막는다):
- `d ::e` — 왼쪽이 떨어진 `::` 는 전역 범위로 판정되어 통과한다.
- `a *-b` — `*` 오른쪽에 단항 부호가 붙으면 데코레이터로 읽혀 통과한다. (오른쪽이 숫자면 잡는다.)
- `int arr[3]` 개행 `= { … };` — 첨자로 끝나는 선언자는 합법인 다중행 대입(`arr[3]` 개행 `= 5;`)과 어휘상 동형이라 놓아 준다.
- 멤버 접근 `->` 와 삼항 `:` 의 개행 — 둘은 §5.5 가상 괄호를 여는 키워드라 §9.1 대상에서 뺐다.
- `operator` 이름(§4.1) — 이름의 일부라 검사 대상이 아니다.

### 2.5 레거시 코드를 처음 반입할 때

규약을 따르지 않던 코드에서는 **표기가 신호가 아니라 소음이다.** sak 의 "위반이다"라는 보고는 여전히 참이지만, 그 자리를 어느 분류로 읽었는지는 작성자의 의도와 다를 수 있다. 첫 정형에서는 **의미를 먼저 확정하고 표기를 새로 쓴다** — sak 의 판정은 힌트로만 받는다. 한 번 규약대로 정형하고 나면, 그 뒤부터는 표기가 곧 신호이므로 sak 을 신뢰해도 된다.

### 2.6 Don't Care — 검출·수정 대상 외

sak 도 사람도 검사·교정하지 않는다. 정본에는 있으나 파이프라인에서 배제.

- **§3 void 외 후행 반환 타입 강제** — vexing parse + 스타일 편차 + 자동 수정 위험.
- **§10.1 네이밍** — 리네임 파급이 커서 자동 판단 위험.
- **§11.1 라행선** — 규약이 "권장 — 부재는 위반 아님" 명문화.

**§1.2·§4·§5.1~§5.3·§6·§7** 은 검사 항목이 아니라 다른 조항들이 딛는 **정의**다. 관심 목록에 넣지 않는다. (표기 판정이 실패하는 자리 — 어느 분류의 합법 표기도 아닌 자리 — 가 곧 §8.4 위반이다.)

## 3. 기계검사 실행 절차

### 3.1 헬퍼 스크립트 (권장)

```sh
.claude/skills/sigma-style/check.sh <file|dir>          # 검사만
.claude/skills/sigma-style/check.sh --edit <file|dir>   # 공백·탭 자동 교정 후 잔여 보고
```

- `build/sak`이 없으면 자동으로 cmake 구성·빌드 후 실행한다(이후엔 기존 `build/` 재사용).
- 디렉터리를 주면 하위까지 재귀(`-r`) 검사한다.
- `--edit` 는 `sak edit` 로 전달 — 간격·구조적 들여쓰기를 자동 교정하고 `[manual]` 잔여를 남긴다.
- **종료코드:** `0` 위반/잔여 없음 / `1` 위반·잔여 있음 / `2` 사용법·경로 오류. 1로 끝나는 건 정상 동작이며 스크립트 실패가 아니다.

### 3.2 직접 실행

```sh
cmake -S . -B build && cmake --build build   # 최초 1회 (또는 ./setup.sh)
./build/sak <file>              # 파일 하나 검사
./build/sak -r <dir>            # 디렉터리 재귀 검사
./build/sak edit <file|dir>     # 공백·탭 자동 교정 (-n/--dry-run 으로 미리보기)
```

### 3.3 출력 파싱

```
<경로>:<행>:<열> [<규칙>] <메시지>
[sak] <N> file(s), <M> violation(s)      # 디렉터리 검사 시 요약 행
```

- 행·열은 1-기준. `<규칙>` 은 `1.1` `1.3` `3` `5.4` `5.5` `5.6` `5.7` `8.2` `8.4` `8.5` `9.1` `9.2` `9.3` `9.4` 중 하나. (`edit` 모드는 각 줄 끝에 `(fixed)` 또는 `[manual]` 를 덧붙인다.)
- 빌드가 불가능한 환경(컴파일러/cmake 부재)이면 1차 기계검사를 건너뛰고 sak 커버 규칙까지 포함해 **전부 수동 검사**로 전환한다.
